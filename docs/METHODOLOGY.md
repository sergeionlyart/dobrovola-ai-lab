# Dobrovola AI Native Lab: базовая методика

## 1. Что мы преподаём

Мы не продаём отдельный навык «писать промпты». Мы учим человека проходить полный цикл создания цифрового продукта вместе с AI-агентами:

```text
Замысел → Контракт → Контекст → План
→ Исполнение → Доказательство → Релиз
```

Продуктом обучения одновременно являются:

- работающий цифровой артефакт;
- документация проекта;
- история решений, задач и проверок;
- способность участника самостоятельно повторить процесс.

## 2. Основной операционный паттерн

```text
Пользователь
  → назначает руководителя и передаёт milestone целиком
Руководитель
  → изучает контекст и выдаёт крупные распоряжения
Исполнитель
  → автономно реализует рабочий пакет и готовит отчёт
Руководитель
  → проверяет доказательства, принимает или возвращает работу
Руководитель
  → интегрирует результаты и закрывает milestone
```

Мы сознательно избегаем микроменеджмента. Пользователь ставит руководителю крупную цель. Руководитель отвечает за milestone в полном объёме. Исполнитель получает законченный рабочий пакет и самостоятельно определяет внутреннюю последовательность действий.

Контроль строится не по числу сообщений и задач, а по критериям, diff, тестам, пользовательскому поведению и другим наблюдаемым доказательствам.

## 3. Семь этапов

### Замысел

Участник определяет пользователя, проблему, ценность и одно основное действие.

### Контракт

Идея превращается в blueprint, границы первой версии, Definition of Done и проверяемые критерии приёмки.

### Контекст

Проект получает короткий `AGENTS.md`, отдельные инструкции ролей, узкие skills и ссылки на канонические документы.

### План

Руководитель изучает milestone целиком, проводит аудит текущего состояния и формирует небольшое число крупных рабочих пакетов. Linear фиксирует цель, состояние, зависимости, решения и доказательства.

### Исполнение

Исполнитель принимает крупный пакет, самостоятельно декомпозирует его на внутренние шаги, реализует все необходимые связанные изменения и готовит результат для независимой приёмки.

### Доказательство

Результат подтверждается diff, commit или PR, тестами, CI, скриншотом или записью сценария, URL, документацией и отчётом исполнителя.

### Релиз

Руководитель проверяет интеграцию. При необходимости аудитор независимо проверяет продукт. Критические дефекты устраняются, после чего версия публикуется и milestone получает честный финальный статус.

## 4. Роли

### Руководитель

Руководитель владеет результатом milestone целиком. Он изучает продуктовые документы и фактическое состояние проекта, формирует крупные поручения, координирует исполнителей, проверяет их отчёты и доводит milestone до полного Definition of Done.

Руководитель не заканчивает работу после составления плана. По умолчанию он не пишет продуктовый код, чтобы не смешивать постановку, исполнение и приёмку.

Каноническая инструкция курса: `starter/roles/leader.md`.

### Исполнитель

Исполнитель владеет результатом порученного рабочего пакета. Он не ждёт пошагового микроменеджмента: самостоятельно изучает код, составляет внутренний план, реализует решение, запускает проверки, исправляет блокирующие дефекты и передаёт руководителю доказательный отчёт.

Свобода исполнителя действует внутри утверждённой цели и scope. Он не меняет продуктовую цель, не добавляет несвязанные функции и не выполняет необратимые действия без полномочий.

Каноническая инструкция курса: `starter/roles/executor.md`.

### Аудитор

Аудитор используется как независимый контур качества. Он преимущественно работает в режиме только чтения, сравнивает результат с критериями, ищет воспроизводимые дефекты и не подменяет исполнителя.

## 5. Активация ролей

В проектном `AGENTS.md` прописана маршрутизация:

- команда `Ты руководитель` активирует инструкцию `roles/leader.md`;
- команда `Ты исполнитель` активирует инструкцию `roles/executor.md`.

Роль сохраняется на сессию и не должна неявно смешиваться с другой ролью.

## 6. Linear и GitHub

Linear — операционный журнал проекта: цель, текущее состояние, крупные рабочие пакеты, блокеры, решения и критерии приёмки.

GitHub — источник артефактов и доказательств: код, документы, история изменений, проверки и релизы.

Ни один из инструментов и ни один отчёт агента не заменяют человеческое решение о качестве результата.

## 7. Правила учебного модуля

- Сначала минимально законченный продукт, затем усложнение слоями.
- Один модуль — один основной пользовательский сценарий.
- Пользователь управляет целями, а не каждым действием агента.
- Руководитель получает milestone, исполнитель — крупный рабочий пакет.
- Каждое занятие заканчивается артефактом и контрольной точкой.
- Красивый результат без работающего сценария не считается готовым.
- Код, созданный агентом, должен быть проверен человеком.
- Отчёт без diff, тестов или другого наблюдаемого доказательства не является приёмкой.
- Инфраструктурная сложность не должна заслонять основной учебный навык.
