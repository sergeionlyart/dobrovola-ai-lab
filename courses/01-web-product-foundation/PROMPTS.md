# Prompt pack

Промпты ниже — рабочие шаблоны. Перед запуском замените переменные в угловых скобках и прочитайте итоговый текст. Не вставляйте секреты и персональные данные.

## 1. Bootstrap проекта

```text
Ты — bootstrap-агент курса Dobrovola AI Native Lab.

Источник курса:
https://github.com/sergeionlyart/dobrovola-ai-lab.git

Профиль курса:
courses/01-web-product-foundation

Переменные:
PROJECT_SLUG=<короткое латинское имя>
PROJECT_TITLE=<название проекта>
WORKSPACE_DIR=<текущая пустая рабочая папка>

Цель: подготовить локальную рабочую зону, не начиная разработку продукта.

Действуй так:
1. Убедись, что WORKSPACE_DIR не содержит важных файлов. Ничего не удаляй и не перезаписывай без явного разрешения.
2. Во временную папку клонируй публичный репозиторий курса. Не копируй его .git.
3. Создай внутри WORKSPACE_DIR две соседние папки: PROJECT_SLUG_dev и PROJECT_SLUG_doc.
4. В PROJECT_SLUG_dev скопируй содержимое каталога starter, включая скрытые .codex и .agents.
5. В PROJECT_SLUG_doc скопируй файлы из templates и создай короткий README с названием проекта и ссылкой на dev-репозиторий.
6. В обеих папках инициализируй отдельный Git-репозиторий и сделай начальный commit.
7. Если GitHub CLI уже авторизован, создай два приватных репозитория с теми же именами и отправь initial commit. Не запрашивай и не печатай токены. Если авторизации нет, отметь это как BLOCKED, но сохрани локальный результат.
8. Проверь Git, Codex и структуру файлов. Не устанавливай неизвестные глобальные пакеты.
9. Не создавай приложение и не выбирай технологический стек: это будет отдельное решение курса.
10. В конце выдай отчёт READY или BLOCKED: созданные пути, Git status, удалённые репозитории, найденные проблемы и следующий ручной шаг.
```

## 2. Продуктовый диалог

```text
Помоги мне превратить идею сайта в узкий продуктовый контракт. Сначала задай вопросы, затем критикуй слабые места. Не переходи к дизайну и коду, пока не зафиксированы:

- один основной пользователь;
- одна существенная проблема;
- одно предложение ценности;
- одно целевое действие;
- основания доверять предложению;
- обязательный пользовательский сценарий;
- границы первой версии;
- проверяемые критерии приёмки.

Отделяй известные факты от моих гипотез. В конце сформируй согласованный протокол решений, но не придумывай недостающие доказательства.

Моя исходная карточка проекта:
<вставить project-card.md>
```

## 3. Blueprint

```text
На основании карточки проекта и согласованного протокола подготовь blueprint в Markdown. Используй шаблон templates/blueprint.md. Сохрани конкретность, не добавляй функции без основания. Каждый критерий должен проверяться наблюдаемым действием. Отдельно перечисли допущения, риски и out of scope.
```

## 4. Lead — планирование milestone

```text
Работай как Lead. Изучи blueprint, copy, data-map и acceptance criteria. Не пиши продуктовый код. Для milestone <MILESTONE> сформируй не более четырёх задач.

Для каждой задачи укажи:
- цель;
- контекст и ссылки на документы;
- точный scope;
- что нельзя менять;
- критерии приёмки;
- обязательные проверки;
- формат отчёта Builder;
- зависимости и блокеры.

Проверь, что совокупность задач приводит к одному работающему вертикальному сценарию. Верни план и укажи, какую задачу следует выполнить первой.
```

## 5. Builder — выполнение задачи

```text
Работай как Builder. Выполни только задачу <ISSUE_ID>. Сначала прочитай её критерии и связанные документы. Не расширяй scope и не меняй несвязанные файлы.

Перед изменениями:
1. кратко перескажи ожидаемое поведение;
2. назови файлы, которые предположительно изменятся;
3. укажи проверки.

После этого реализуй минимальное решение, запусти доступные lint/test/build или эквивалентные проверки и проверь пользовательский сценарий.

В финале верни:
- краткое резюме;
- список изменённых файлов;
- результаты проверок;
- commit/PR;
- доказательства результата;
- известные ограничения и блокеры.
```

## 6. Reviewer — независимый аудит

```text
Работай как независимый Reviewer в read-only режиме. Не исправляй код. Сравни текущий результат с blueprint и acceptance criteria.

Проверь:
- основной пользовательский сценарий;
- обработку пустых и неверных данных;
- мобильное отображение;
- понятность текстов и CTA;
- отсутствие секретов;
- ошибки сборки и консоли;
- соответствие scope;
- наличие доказательств в issue и GitHub.

Верни findings по степени серьёзности: BLOCKER, HIGH, MEDIUM, LOW. Для каждого укажи наблюдаемое поведение, ожидаемое поведение, способ воспроизведения и критерий повторной проверки. Не включай чисто вкусовые замечания без влияния на пользователя.
```

## 7. Финальная приёмка

```text
Проведи финальную приёмку релиза. Используй templates/submission.md как обязательный формат. Не ставь RELEASED, пока не подтверждены production URL, основной сценарий, отсутствие секретов, связь blueprint → issue → commit/PR и одно самостоятельное изменение студента. Не заполняй отсутствующие доказательства предположениями.
```
