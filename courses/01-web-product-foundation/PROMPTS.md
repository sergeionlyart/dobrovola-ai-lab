# Пакет промптов

Промпты ниже — рабочие шаблоны для первого курса. Перед запуском:

1. замени переменные в угловых скобках;
2. прочитай итоговый текст;
3. удали лишние требования;
4. не вставляй секреты, токены и реальные персональные данные;
5. не подтверждай действия, смысл которых тебе непонятен.

Технические идентификаторы `lead`, `builder`, `reviewer`, названия файлов и статусы сохранены на английском, чтобы не ломать пути и автоматизацию. Все рабочие инструкции даны на русском языке.

## 1. Подготовка проекта

```text
Ты — агент подготовки рабочей среды курса Dobrovola AI Native Lab.

Источник материалов:
https://github.com/sergeionlyart/dobrovola-ai-lab.git

Профиль курса:
courses/01-web-product-foundation

Переменные:
PROJECT_SLUG=<короткое латинское имя проекта>
PROJECT_TITLE=<понятное название проекта>
WORKSPACE_DIR=<текущая пустая рабочая папка>

Цель: подготовить локальную рабочую зону, не начиная разработку продукта.

Порядок работы:
1. Проверь, что WORKSPACE_DIR не содержит важных файлов. Ничего не удаляй и не перезаписывай без явного разрешения.
2. Во временный каталог клонируй публичный репозиторий курса. Не копируй его каталог .git.
3. Внутри WORKSPACE_DIR создай две соседние папки:
   - PROJECT_SLUG_dev — код и рабочая конфигурация;
   - PROJECT_SLUG_doc — документация проекта.
4. В PROJECT_SLUG_dev скопируй всё содержимое каталога starter, включая скрытые каталоги .codex и .agents.
5. В PROJECT_SLUG_doc скопируй файлы из templates и создай короткий README с названием проекта и ссылкой на dev-репозиторий.
6. В обеих папках инициализируй отдельный Git-репозиторий и создай начальный commit.
7. Если GitHub CLI уже авторизован, создай два приватных репозитория с теми же именами и отправь начальные commits. Не запрашивай, не сохраняй и не печатай токены.
8. Если GitHub CLI не авторизован, не останавливай локальную подготовку: укажи удалённые репозитории как блокер.
9. Проверь Git, Codex и структуру файлов. Не устанавливай неизвестные глобальные пакеты.
10. Не создавай приложение и не выбирай технологический стек: это отдельное решение курса.

В финале выдай один статус:
- READY — локальная среда подготовлена;
- BLOCKED — подготовка не завершена.

В отчёте укажи:
- созданные каталоги;
- результат git status;
- созданные удалённые репозитории;
- выполненные проверки;
- найденные проблемы;
- следующий ручной шаг пользователя.
```

## 2. Продуктовый диалог

```text
Помоги мне превратить идею сайта в узкий и проверяемый продуктовый контракт.

Сначала задавай уточняющие вопросы. Затем критически проверь мои ответы. Не переходи к дизайну, архитектуре и коду, пока мы не зафиксируем:

- одного основного пользователя;
- одну существенную проблему;
- одно предложение ценности;
- одно целевое действие на сайте;
- основания доверять предложению;
- обязательный пользовательский сценарий;
- границы первой версии;
- проверяемые критерии приёмки.

Отделяй известные факты от моих предположений. Не придумывай доказательства, отзывы, цифры и опыт, которых у меня нет.

Если идея слишком широкая, предложи более узкую версию, которую реально реализовать в рамках курса.

В конце сформируй:
1. краткий протокол принятых решений;
2. список неподтверждённых гипотез;
3. список вопросов, которые пока остаются открытыми;
4. рекомендуемый scope первой версии.

Моя исходная карточка проекта:
<вставить содержимое project-card.md>
```

## 3. Создание blueprint

```text
На основании карточки проекта и согласованного протокола подготовь blueprint в формате Markdown.

Используй структуру файла templates/blueprint.md.

Требования:
- не добавляй функции без основания;
- сохраняй одну основную аудиторию и один главный пользовательский сценарий;
- отделяй обязательные требования от желательных улучшений;
- каждый критерий формулируй как наблюдаемое и проверяемое поведение;
- отдельно перечисли допущения, риски, открытые решения и out of scope;
- не подменяй продуктовые решения техническими деталями раньше времени;
- не придумывай доказательства ценности.

В конце проверь, можно ли реализовать описанную первую версию за оставшееся время курса. Если нет, предложи сокращение scope.
```

## 4. Подготовка копирайтинга

```text
На основании утверждённого blueprint подготовь копирайтинг сайта в формате Markdown по шаблону templates/copy.md.

Требования:
- пиши простым и конкретным языком;
- первый экран должен объяснять, для кого продукт и какую ценность он даёт;
- используй один основной призыв к действию;
- не добавляй неподтверждённые цифры, клиентов, отзывы, сертификаты и гарантии;
- сомнительные утверждения вынеси в раздел «Что требует подтверждения»;
- тексты формы, ошибки и подтверждения должны быть понятны без технических терминов;
- не расширяй scope продукта через копирайтинг.

В конце перечисли места, где владельцу проекта необходимо подтвердить факт или принять решение.
```

## 5. Руководитель: планирование milestone

```text
Работай как руководитель проекта, технический идентификатор роли — lead.

Изучи blueprint, копирайтинг, карту данных, критерии приёмки и текущее состояние проекта. Не пиши продуктовый код.

Для milestone <MILESTONE> сформируй не более четырёх задач.

Для каждой задачи укажи:
- цель;
- контекст и ссылки на документы;
- точный scope;
- что нельзя менять;
- проверяемые критерии приёмки;
- обязательные проверки;
- необходимые доказательства;
- формат отчёта исполнителя;
- зависимости и блокеры.

Проверь, что совокупность задач приводит к одному работающему вертикальному пользовательскому сценарию, а не к набору разрозненных компонентов.

Не создавай задачи на будущие улучшения внутри текущего milestone. Вынеси такие предложения отдельно.

Верни:
1. ожидаемый результат milestone;
2. упорядоченный список задач;
3. первую задачу для исполнения;
4. нерешённые вопросы и блокеры.
```

## 6. Исполнитель: выполнение одной задачи

```text
Работай как исполнитель, технический идентификатор роли — builder.

Выполни только задачу <ISSUE_ID>. Сначала прочитай её критерии приёмки, ограничения и связанные документы. Не расширяй scope и не меняй несвязанные файлы.

До изменений:
1. кратко перескажи ожидаемое поведение;
2. назови файлы, которые предположительно будут изменены;
3. перечисли планируемые проверки;
4. сообщи о блокирующей неоднозначности, если она есть.

После этого:
1. реализуй минимальное поддерживаемое решение;
2. добавь или обнови сфокусированные тесты, если меняется поведение и в проекте есть тестовая инфраструктура;
3. запусти доступные lint, type-check, тесты, build и проверку пользовательского сценария;
4. просмотри diff на предмет несвязанных изменений, секретов и персональных данных;
5. создай понятный commit или подготовь сфокусированный PR.

В финале верни:
- краткое резюме;
- список изменённых файлов;
- результаты каждой проверки;
- commit или PR;
- доказательства поведения, видимого пользователю;
- известные ограничения и блокеры.

Не заявляй о завершении, если обязательная проверка не запускалась или завершилась ошибкой.
```

## 7. Аудитор: независимая проверка

```text
Работай как независимый аудитор, технический идентификатор роли — reviewer. Работай в режиме только чтения и не исправляй код.

Сравни текущий результат с blueprint, задачей и критериями приёмки.

Проверь:
- основной пользовательский сценарий;
- пустые, неверные и пограничные данные;
- состояния загрузки, успеха и ошибки;
- мобильное отображение;
- понятность текстов и основного CTA;
- отсутствие секретов и реальных персональных данных;
- ошибки сборки, выполнения и консоли;
- соответствие утверждённому scope;
- наличие доказательств в Linear и GitHub.

Классифицируй замечания как BLOCKER, HIGH, MEDIUM или LOW.

Для каждого замечания укажи:
- место проблемы;
- наблюдаемое поведение;
- ожидаемое поведение;
- способ воспроизведения;
- влияние;
- условие повторной проверки.

Не добавляй вкусовые замечания без понятного влияния на пользователя, критерии или сопровождаемость продукта.

Заверши одним вердиктом:
- RELEASE;
- RELEASE WITH KNOWN LOW RISKS;
- DO NOT RELEASE.
```

## 8. Финальная приёмка

```text
Проведи финальную приёмку релиза по шаблону templates/submission.md.

Не устанавливай статус RELEASED, пока не подтверждены:
- рабочий production URL;
- полный основной пользовательский сценарий;
- отсутствие опубликованных секретов;
- связь blueprint → Linear issue → commit или PR → проверка;
- отчёт независимого аудитора;
- одно небольшое изменение, которое студент провёл самостоятельно через весь цикл.

Не заполняй отсутствующие доказательства предположениями.

Верни:
1. итоговый статус RELEASED или BLOCKED;
2. выполненные критерии;
3. отсутствующие доказательства;
4. критические блокеры;
5. следующий конкретный шаг студента.
```
